# Gift & Glam 2026 — cinematic tree, gifts and donations

This patch is incremental on `interactive-tree-donations` (PR #6, verified commit `998dd2047b2b92aeba89e18ad27de2154131480e`, based on main `588fffe8a84c870777e80720302e0c3b83665f2c`). Apply against that branch, or against main only if it already contains PR #6. The 2027 PR #2 is out of scope. Run `git apply --check` first; stop on unexpected divergence. The cinematic WebP asset is included in the binary patch; no external asset dependency or new package is needed.

## What's included

- The approved cinematic tree layout, original festive font and top lights, left-side campaign summary and button, color-coded clickable ornaments, filters, gift details below the tree, sparkles on selection, confetti after a successful adoption, and the real email/contact form and thank-you instructions. The tree displays only published angel codes; no fictional data in production.
- Personalized sponsor confirmation email built from `toPublic`, shopping list/sizes/optional cards, private My Angels link, printable label and downloadable list. Visible email API acceptance or failure; no claim rollback on email failure. My Angels also lets donors recover access using their code and email (or email alone if they forgot the code/released the last angel). Recovery sends only to recorded email, returns a generic response, and rate limits requests; never gives a token to someone who merely knows an angel code.
- Individual gift records, donor purchase checkboxes, Done shopping separate from item purchases, organizer receipt and donation assignment, By Angel and By Gift views, filters, actual counts and links to private household/child profiles. A received gift may have an unknown purchase source; check both purchase and receipt filters. Removed list items retain their history and are hidden by default. Replacing a sponsor clears unreceived sponsor purchase marks, not organizer receipts.
- Donation purposes: Gift of a Store Gift Card (optional store), To Purchase Additional Angel Gifts, Toward Party Expenses, and Other Ways to Give (volunteering, sorting, collection, supplies/services, gifts or another offer). Purpose-specific payment memo, existing payment options, optional donation-intention recording, non-financial offer form, private Donations & Volunteers page with pending/received/contacted/closed workflow and verified received totals by purpose. No payment processing, card/PIN collection, or automatic payment confirmation. Donation assignment of an item is not a bank transaction and does not debit a budget.
- Browser-only 21-column CSV intake with existing family deduplication, age-unclear flag, separate gift card entries, source and notes. Separate items with semicolons; additional cards use `Store | Amount; Store | Amount`. Missing gift-card amounts remain blank pending organizer review; extra interests beyond public three are retained in private notes. CSV is deterministic and no AI call is made. The review-only PDF/email button deliberately loads a labeled fictional sample without transmitting a real source file.

## Migration and deployment order

1. Do not change the existing production database while evaluating the draft PR. Review the new migration `supabase/migrations/20261125140000_gift_cycle.sql` and test the existing migration chain plus this additive migration against disposable PostgreSQL/Supabase. It creates `gift_items`, `donation_offers`, and restricted service-role RPCs, with RLS and no anon/authenticated data grants. No existing child/family/sponsor record is overwritten. It backfills the actual wish/need/card requests; it does **not** infer individual purchase or receipt status from the old whole-child status. Existing status stays intact. Use the organizer's evidence to reconcile legacy per-item receipts.
2. Run `npm test`, `npm run typecheck`, `npm run build`. Confirm permission grants and run Supabase security advisors on authorized test environment. Use review mode and fictional families only. Do not link a review build to production data or send real sample emails/payments.
3. Verify `RESEND_API_KEY`, `ANGEL_FROM_EMAIL` (verified sender), `NEXT_PUBLIC_SITE_URL`, drop-off env values, and actual recipient handles with the organizer. No secrets in source or logs. The preview blocks real payment-link display and mail sending. The real Anthropic parser still needs a safe fictional-email production test, working key, and privacy approval; CSV/manual intake is the zero-AI-cost path.
4. Provide updated PR #6 preview and wait for owner approval. When separately approved for production, back up/record existing row counts, apply **only** this additive migration to Gift & Glam production (not another app), verify backfill/permissions and row counts, then merge and redeploy the approved code. Do not run seed/reset or touch existing records. Existing live app code predates these tables, so migration must precede deployment of the new code.
